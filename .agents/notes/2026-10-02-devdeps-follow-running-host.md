# 决策：devDeps 跟到宿主 0.2.0 线，engines.dsh 下限不动（2026-10-02）

状态：生效

## 问题

本仓 devDeps 锁在 `0.1.7-rc.2` 编译，而实际运行的宿主已是 `0.2.0-rc.2`。
错位的后果不是「编译报错」而是「编译通过、运行时崩」—— 类型是按旧宿主核的，
实际宿主的行为与契约可能已经变了。

## 决策

**devDeps 升到 `0.2.0-rc.2`（21 个宿主线包），`engines.dsh` 保持 `>=0.1.7-rc.2` 不动。**

升级过程中被带出的连带项：`dsh-llm-pi-ai@0.2.0-rc.2` 把它的传递依赖
`@earendil-works/pi-ai` 从 `^0.85.1` 抬到 `^0.87.1`。本仓原本写死 `0.85.1`，
于是 pnpm 装出**两份 pi-ai**（顶层 0.85.1 + 嵌套 0.87.1），类型互不兼容，
`adapter.ts` 报 `Provider<0.85.1>` 不能赋给 `Provider<0.87.1>`。
处置：本仓那份改成 `^0.87.1`（与宿主同源的范围，不写死），重复副本消失、两半 tsc 归零。

## engines.dsh 为什么不动

下限的意义是「声明支持哪条线」，不是「只在最新线上验过」。两条线都实测过：

在**仓库外**的临时目录装 `dsh-llm@0.1.7-rc.2` + `dsh-llm-pi-ai@0.1.7-rc.2`，
用本仓真实的 `createProvider` 调用形态（`auth` 具名解析器 + `openAICompletionsApi()` 调用
+ `models`）编译：

| 组合 | 结果 |
|---|---|
| 0.1.7 宿主 + pi-ai 0.87.1 | tsc 0 错误 |
| 0.1.7 宿主 + pi-ai 0.85.1 | tsc 0 错误 |
| 0.2.0 宿主 + pi-ai 0.87.1（本仓当前） | tsc 0 错误 |

即：本仓用到的宿主符号（`createProvider` / `Provider` / `openAICompletionsApi` /
`PiAiAdapter` / `ResolvedPiAiProviderProfile` / `resolveRetryPolicy` / `LlmModelInfo`）
在 0.1.7 与 0.2.0 两条线上形状一致，`pi-ai` 0.85→0.87 的 `Context` → `TranscriptContext`
改名**没有触及本仓** —— 那个参数由宿主内部传入，本仓只透传。

所以下限不动是**有实测支撑的**，不是「大概能跑」。

## 替代方案

- **把 `engines.dsh` 一起抬到 `>=0.2.0-rc.2`**：能省掉「要同时照顾两条线」的负担，
  但会把已经能用 0.1.7 的用户挡在门外，而没有任何收益 —— 实测两条线都过。
  抬下限应当是**代码真的不兼容时**的动作，不是跟随升级的仪式。
- **把 pi-ai 写死成 `0.87.1`**：能消掉重复副本，但宿主下次抬传递依赖时同样会错位，
  且写死会在宿主用 `^` 时多装一份。用 `^` 与宿主保持同一种范围语义。
- **不动 devDeps，只加文档提醒**：等于把「编译通过、运行时崩」的风险留给下一次改动。

## 影响

- 核验兼容性要装**另一条线**的宿主包，必须用**仓库外**的临时目录：
  在仓内建目录会被 pnpm 当作 workspace 成员，`pnpm add` 会顺带重排本仓的 `node_modules`。
- 升级 devDeps 与 `engines.dsh` 是**两个独立判断**：前者跟运行中的宿主，后者看代码实际兼容范围。
- 这条规则（含「两份同名包」的判据）写进根 [AGENTS.md](../../AGENTS.md) 的活跃坑，另两个插件仓同批各写一份。
